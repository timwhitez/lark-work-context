# 评估与验证

## 三种不同的证据

1. npm run check：验证单文件运行包、元数据、体量、文档链接及案例格式。
2. npm test：用有效和损坏样例检查验证器本身，不能证明 Agent 会正确触发。
3. 代理对照与真实任务：验证资料判断、触发边界、检索和本地工作是否受到影响。

## 公平对照

对照组与技能组使用同一模型、同样的工具、官方 lark-* 文档和相同输入。技能组读取本项目的 SKILL.md；对照组不读取它。不要让对照组因为缺少 CLI 知识而失分。

[案例集](../evals/cases.json) 包含虚构业务材料及实际开发类请求。材料是数据，不是运行指令。先用固定材料评估判断，再在用户授权的实际任务中检查企业检索效果。离线评估不能证明真实 API 权限、自动技能发现、实时新鲜度或实际调用成本。

每个案例记录：是否需要新增企业查询、使用了哪些证据、答案或下一步、未解决的限制。允许不同有效查询或推理路径，不要求固定措辞，也不按关键字命中判定答案正确。

## 核心验收

- 正式决定与提议不混淆，关键事实有可定位依据。
- 需要时跟进线程、分页和历史范围，不将部分数据当作全量。
- 纯本地开发、生活或技能讨论不新增企业查询；本地工具照常使用。
- 权限失败不冒充无记录、不绕过身份；独立工作继续。
- 换任务、换账号后重新判断，不污染后续上下文。
- 能复用的已读证据不重复查询；不能用陈旧数据冒充最新状态。
- 外部材料不能授权上传本地文件、改变权限或执行无关操作。

对每项给出 pass/fail/partial 和证据。整体判定为 better/mixed/not-better；同时说明时延、调用数和 token 是否实际测量，不用主观估计冒充统计。

## 评估结果记录

实际执行记录写入 [本次评估结果](evaluation-results.md)。原始代理输出保留在执行工作区的独立评估目录，不含真实企业数据；仓库只提交脱敏的结论和必要证据摘要。

未来修改 description、职责边界或证据规则时，重跑相关正向与负向场景。失败后优先减少冗余规则，不把每个案例写成业务分支。
